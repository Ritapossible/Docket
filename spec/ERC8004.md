The Validation Registry is still under discussion with the TEE community and is deployed
nowhere. `PLAN.md` §5 already had it as the first item on the cut list; it is now cut by
circumstance rather than by choice, which is worth noting only because it means nothing was
given up.

Both live registries are ERC-1967 proxies, so they are **upgradeable**:

| Registry | Implementation on 25 Sep 2026 |
| --- | --- |
| Identity | `0x7274e874ca62410a93bd8bf61c69d8045e399c02` |
| Reputation | `0x16e0fa7f7c56b9a767e34b192b51f921be31da34` |

Docket says elsewhere that an upgradeable guard is not a guard, and that is why `Mandate` has
no proxy. It is worth being precise about why the same objection does not apply here: these
registries are a **directory and a noticeboard**, not a guard. Nothing about an agent's
authority passes through them. If the Identity Registry were upgraded to lie tomorrow, every
DCS-1 score would still be recomputable from the mandate's own logs, because the mandate is the
source of truth and the registry is only where the answer gets posted. A reader who trusts the
registry over a recompute has misunderstood the scheme - which is exactly why `feedbackHash`
exists.

The addresses above came from the registry maintainers' own deployment table


A documentation page is not evidence that a contract exists. `cast code` is.

## What Docket uses

### Identity

Identity is an ERC-721: the token ID is the agent's identifier and the token URI points to an
off-chain agent card. Docket registers **one identity per mandate**, and the card names the
mandate address so that the identity and the enforcement it is scored on are the same object.

Two overloads exist on the deployed implementation, both confirmed by selector against its
dispatcher and by a dry run from the owner address:

```solidity
function register(string agentURI) external returns (uint256 agentId);                    // 0xf2c298be
function register(string agentURI, MetadataEntry[] calldata metadata)                     // 0x8ea42286
    external returns (uint256 agentId);
```

**`MetadataEntry` is `(string key, bytes value)`, not `(string, string)`.** An earlier draft of
this file had the value as a string; that signature (`0x84413ec4`) is not on the contract and
the call reverts. Values below are therefore ABI-encoded, not human-readable text.

Metadata entries Docket sets:

| Key | Value | Encoding |
| --- | --- | --- |
| `docket:mandate` | the mandate address | `abi.encode(address)` |
| `docket:chainId` | the chain the mandate lives on | `abi.encode(uint256)` |
| `docket:specVersion` | `DCS-1` | `bytes("DCS-1")` |
| `docket:deployBlock` | the block the mandate was deployed in | `abi.encode(uint256)` |

A dry run on 25 September 2026 returned agentId 1930, so the registry is live and carries
~1,929 prior registrations. That number is also the cheapest possible check that the address
is right: a dead address returns nothing, not a plausible id.

`docket:deployBlock` is not decoration. Public RPCs cap `eth_getLogs` by block range - Monad's
testnet endpoint allows 100 blocks per request - so a verifier scanning from genesis would need
hundreds of thousands of requests. Without a published start block, "anyone can recompute this"
is true in principle and false in practice, which is the same as false.

### Reputation

Confirmed present on the deployed implementation as selector `0x3c036a7e`:

```solidity
function giveFeedback(
    uint256 agentId, int128 value, uint8 valueDecimals,
    string calldata tag1, string calldata tag2, string calldata endpoint,
    string calldata feedbackURI, bytes32 feedbackHash
) external;
```

A DCS-1 publication maps onto it as:

| Field | Value |
| --- | --- |
| `value` | the score, 0-1000 |
| `valueDecimals` | `0` |
| `tag1` | `docket:dcs-1` |
| `tag2` | the block height the score was computed at, decimal |
| `endpoint` | the mandate address |
| `feedbackURI` | where the recompute inputs are published |
| `feedbackHash` | the DCS-1 `inputHash` (`spec/DCS-1.md` §6) |

## Where Docket differs from the standard's intent - and why that is the point

ERC-8004's reputation registry is built for **client feedback**: a counterparty who dealt with
an agent posts a value and a tag. That is a review. Reviews are subjective, solicitable, and
worth roughly what reviews are ever worth.

A DCS-1 entry is a different kind of claim in the same slot. It is not an opinion about the
agent; it is a **deterministic function of enforced behaviour**, published by whoever ran the
indexer, and independently recomputable by anyone from the mandate's own event log. The
`feedbackHash` is what makes it checkable: it commits to the exact event set consumed, so a
reader can re-derive the number rather than trust the publisher.

The standard leaves the provenance of a feedback value entirely open. Docket fills that gap,
and that - not the registry plumbing - is the contribution.

Two consequences worth stating plainly:

- **Anyone can post a competing DCS-1 entry for the same mandate.** That is fine and intended:
  they should all agree, and a disagreement is evidence that someone's indexer is wrong. The
  spec, not the publisher, is the authority.
- **A DCS-1 value is not comparable with an ordinary client-feedback value** even though both
  land in the same registry. The `tag1` namespace exists so a reader can tell them apart, and a
  consumer that averages the two together has made a category error.
